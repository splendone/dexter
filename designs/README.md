# designs 使用说明(工程设计规格书)

**G2「工程设计规格」的产出落点**——Dexter 从"读与报"扩到"设计与交付规格"之后的
落点。制度依据:宪法 v1.4「设计与实验支持」。

## 分工(硬的)

| 谁 | 做什么 |
|---|---|
| **Dexter** | 出**规格与判据**:方案、选型、BOM、接口、步骤、验收判据、失败模式、风险 |
| **真实世界的人** | **采购、付款、动手制作、跑实验、反馈实测结果** |

Dexter **不代做、不遥控**。规格书里不得出现"我将采购 / 我将焊接 / 我将跑实验"
这类越界表述——出现即删。

## 流转

1. 草稿写入本目录,文件名 `<主题>-规格书-v0.x.md`,文件头带署名链:
   `起草 = Dexter(YYYY-MM-DD) | 复核 = Dexter 自查(…) | 签发 = …`;
2. 走「会签前自查复核」(独立子任务重读 + **外部交叉源**:datasheet、官方文档、
   供应商页面),通过后**自审签发 = v1.0**;
3. **真人实测反馈回来后必须升版本**(v1.1、v1.2 …),文末"修订记录"追加条目
   ——**规格书是活文档**;**未验证的规格不得标"已验证"**;
4. **三条红线(交付前升级门)**:
   ① 涉及**人身安全**(力 / 温 / 电 / 运动范围)→ 委托人复核后才可交付执行;
   ② 涉及**大额采购**(超预设额度)→ 委托人先批预算;
   ③ 涉及**危险操作 / 对外协作**→ 只写"需资质 / 需委托人出面"。

## 规格书骨架(八项要件,缺一即不合格)

### 0. TL;DR 与适用边界

一段话说清:解决什么问题、系统长什么样、总预算量级、预计工期、**不解决什么**。

### 1. 问题定义与验收目标

- 要达成的能力(可观测的行为描述,不是"实现灵巧操作"这类不可测目标);
- **验收判据**(可测量:成功率 / 节拍 / 精度 / 连续运行时长 / 成本上限);
- 明确**不达标即失败**的底线。

### 2. 系统构成与工作原理

- 子系统分解(机械 / 传感 / 驱动 / 计算 / 供电);
- 一张构成图(方块图或接口图);
- 工作原理一段:为什么这样就能达成验收判据。

### 3. 硬件选型与 BOM

| 项 | 型号 / 规格 | 数量 | 供应商 | 价格区间 | 交期 | 选型理由 | 出处 |
|---|---|---|---|---|---|---|---|
|  |  |  |  |  |  |  |  |

- 关键件须给**替代方案**(断供 / 涨价时的 B 计划);
- 无法确认的参数标"**待实测**"或"待询价",不得估一个数字充数。

### 4. 接口定义

- 机械接口(安装孔位 / 法兰 / 行程包络);
- 电气接口(电压 / 电流 / 通信协议 / 线序);
- 软件接口(API / SDK / 版本 / 驱动)。

### 5. 软件栈与依赖

- 框架与版本(如 ROS 2 / Isaac Lab / PyTorch 的具体版本号);
- 许可(开源协议、商用限制);
- 环境搭建步骤与已知坑。

### 6. 实施步骤

按阶段编号,**每步写清"做完的标志"**;目标是**可被未参与讨论的工程师照做**。

### 7. 验收测试方案

- 测试项 × 通过标准 × 样本量 × 记录方式;
- 若含**真实世界实验设计**:自变量 / 因变量 / 对照 / 样本量 / 统计判据 /
  混杂控制。

### 8. 失败模式表与风险

| 症状 | 可能原因 | 排查动作 | 缓解措施 |
|---|---|---|---|
|  |  |  |  |

- **残余不确定性清单**(Dexter 必须主动列,不许藏);
- 安全与合规提示;
- 未解问题与需要委托人决策的点。

## 边界

- 规格书**不等于**可行性担保。Dexter 没有手、没有钱、没有实验室;
  **残余不确定性必须写在纸面上**。
- 涉及**人身安全 / 大额采购 / 危险操作**的规格,签发后仍**须委托人复核**
  才可交付执行。
- 规程详见 `.zcode/skills/design-spec`。
- **产物依赖**:本目录产物的"上位依据 / 下游产物"见
  `knowledge/maps/artifact-dependencies.md`;规格书内的**残余不确定性**须同步登记
  `knowledge/maps/assumptions.md`(假设账本),被证伪时据此触发下游重审。
