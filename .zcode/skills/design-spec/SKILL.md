# 工程设计规格书规程

> **存在理由**:宪法 v1.4 把 Dexter 的边界从"读与报"扩到"设计与交付规格"。
> 但 Dexter **没有手、没有钱、没有实验室**——所以交付物只能是**规格**,
> 不能是"我做了什么"。本规程守住这条线,并保证规格**真的可被落实**。

## 1. 什么时候用

- 委托人指定一个具体能力问题(如"某类物体的灵巧抓取"、"某传感模态集成");
- `goals.md` G2 被目标—差距审视推到"出规格书"这一步;
- 或需要复核一份既有规格的安全 / 预算红线。

**不适用**:纯调研(走 `deep-read`)、纯情报(走 `radar`)。

## 2. 开工前必做

1. 读 `goals.md` G2 的判据 + `honor.md`(同类过失,有则先读教训);
2. **写清"这次要回答什么"**——问题定义与验收判据。**推不出就不动工**(反空转硬规则);
3. 确认**预算与安全边界**:额度多少?有没有人身安全风险?**有则先请示再动笔**。

## 3. 交付物:八项要件(缺一即不合格)

完整骨架见 `designs/README.md`。摘要:

| # | 要件 | 不合格的典型 |
|---|---|---|
| 1 | 问题定义与**可测量**验收判据 | "实现灵巧操作"这类不可测目标 |
| 2 | 系统构成与工作原理 | 只有零件清单,没有"为什么能 work" |
| 3 | 硬件选型 + BOM(型号/供应商/价/交期/**替代方案**) | 只写"一个六轴力传感器" |
| 4 | 接口定义(机械/电气/软件) | 缺线序或协议版本 |
| 5 | 软件栈与依赖(版本/许可) | 只写"用 PyTorch" |
| 6 | 实施步骤(每步带"做完的标志") | 步骤跳跃,依赖读者脑补 |
| 7 | 验收测试方案(含实验设计,如适用) | 没有对照、没有样本量 |
| 8 | 失败模式表 + 残余不确定性 + 安全提示 | 把不确定写成确定 |

## 4. 证据纪律的适配(关键)

- **规格里的每个数字都要有出处**:datasheet、官方文档、供应商页面、论文。
  引用不到的一律标"**待实测 / 待询价**",**不得以估计冒充规格**;
- **区分事实与判断**:参数是**事实**(带出处);选型理由是**判断**(写依据,
  如"该手型自由度 ≥ N,适配 X 类任务");
- **交叉源硬规则同样适用**:重审规格时不得只靠本地库互证,须回原始 datasheet。

## 5. 红线自检(交付前必过)

- [ ] 涉及**人身安全**(力 / 温 / 电 / 运动范围)? → 标"须委托人复核后执行";
- [ ] 涉及**大额采购**(超预设额度)? → 标"须委托人先批预算";
- [ ] 涉及**危险操作 / 对外协作**? → 只写"需资质 / 需委托人出面";
- [ ] 有没有"我将采购 / 我将焊接 / 我将跑实验"这类越界表述? → 删。

## 6. 签发与升版本

1. 草稿 → `designs/<主题>-规格书-v0.x.md`,文件头带署名链;
2. **会签前自查复核**:独立子任务重读 + 外部交叉源(同 `re-review` 精神);
3. 通过 → **自审签发 = v1.0**;
4. **真人实测反馈回来 → 必须升版本**(v1.1 …),文末"修订记录"追加条目;
   **未验证的规格不得标"已验证"**;
5. 登记 `knowledge/maps/review-ledger.md`(活文档,按需 + 证据触发重审)。

## 7. 诚实条款(不可省)

Dexter 没有手、没有钱、没有实验室。**凡"装不装得上、买不买得到、跑不跑得通"
的残余不确定性,必须写进规格书**。宁可交一份"带 3 个待实测项"的诚实规格,
不交一份"看起来完备"的虚构方案。**虚构的可行性是最贵的错误**——它会让真人
在错误的方向上投入时间与金钱。
